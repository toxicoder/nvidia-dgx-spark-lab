Developer Environment

Multi-arch devcontainer and host setup so anyone can contribute on Apple Silicon, Windows, Linux, or DGX Spark.

Developer Environment

What this enables

  • Opening the repo on almost any workstation and matching CI tooling
  • Contributing to scripts, Kubernetes YAML, dashboard, and docs without a GPU cluster
  • Avoiding “works on my machine” version skew

Software contribution vs cluster ops

This page is for writing and testing code in this repository.
Bringing up K3s on DGX Spark nodes is covered in Getting Started.

Branching model

  • Primary integration branch: development (protected, PR-required).
  • Branch all feature work from development and open PRs into development.
  • Promotion path: feature → development → (optional) dev → main (always via PR).
  • Never force-push development or main.
  • Protected branches require linear history — merge with squash or rebase (merge commits are blocked).

Supported platforms

The contributor image is Linux multi-arch (linux/amd64 + linux/arm64). The same .devcontainer/ definition runs on:

HostCPUHow it runs
macOS Apple Siliconarm64Docker Desktop → arm64 Linux container
macOS Intelx86_64Docker Desktop → amd64 Linux container
Windows 10/11x86_64Docker Desktop + WSL2 → amd64 Linux container
Linux workstationamd64 or arm64Docker Engine / Podman → matching arch
NVIDIA DGX Sparkarm64 (Grace)Docker/Podman on the Spark → arm64 Linux container
GitHub Codespacestypically amd64Uses .devcontainer/ automatically

The container is always Linux. Native Windows containers are out of scope (this toolchain is Linux-native). On Windows, clone on the WSL2 filesystem, not /mnt/c.

No GPU is required for unit tests, lint, docs, or dashboard Vitest. GPU nodes matter only when you operate real workloads.

Tool pins live in .devcontainer/tool-versions.env and are shared with CI.

Recommended: Dev Container

Prerequisites

  1. Docker
    • macOS / Windows: Docker Desktop
    • Linux / DGX Spark: Docker Engine or Podman with a Docker-compatible socket
  2. VS Code, Cursor, or Codespaces with the Dev Containers extension
  3. ~8 GB RAM and ~32 GB free disk (see hostRequirements in devcontainer.json)

Open the container

  1. Clone the repository.
  2. Open the folder in VS Code / Cursor.
  3. Command Palette → Dev Containers: Reopen in Container.
  4. Wait for image build (first time) + post-create (npm + docs + doctor).

Agent CLIs and secrets

Grok Build is in the image at /usr/local/bin/grok (pin + checksum in tool-versions.env). Post-create still runs .devcontainer/install-agent-clis.sh (skip with DEVCONTAINER_SKIP_AGENT_CLIS=1): it no-ops Grok when the pin matches, and installs Hermes with --skip-setup --non-interactive. Installers never write API keys and never run setup wizards during create.

The container can reach LLM providers on the host at http://host.docker.internal:<port>/v1 (LiteLLM/vLLM on the workstation) and cloud APIs (api.x.ai, …) over ordinary egress. devcontainer.json adds host.docker.internal → host-gateway so this works on Docker Desktop and Linux Engine. Do not use --network=host.

Default sandbox is GROK_SANDBOX=lab: workspace writes, kernel-deny of /var/run/docker.sock and typical secret globs (**/.env, **/*.pem). Humans can still run docker for hermetic tests. Override with GROK_SANDBOX=off or workspace if you need the agent to talk to Docker. Copy .devcontainer/host-llm.example.toml into ~/.grok/config.toml to register a host model.

Never commit agent credentials

Do not put GROK_DEPLOYMENT_KEY, OpenRouter/OpenAI/etc. keys, or Hermes auth files in the repo, in devcontainer.json env blocks, or in screenshots of create logs. Auth lives only on Docker volumes or your host home dir. See SECURITY.md.

Hermes on the Spark host (Docker gateway stacks) is documented separately in hermes-agent.md.

Lifecycle (optimized):

  1. Image build — independent fetch stages (Dockerfile). CI publishes ghcr.io/toxicoder/nvidia-dgx-spark-lab/devcontainer for layer cache (native linux/amd64 + linux/arm64). After the first successful publish, set that GHCR package public so anonymous clones can use build.cacheFrom. Lab runtime images (lab-dashboard, mcp-*, coder-workspace) use the same GHCR namespace via .github/workflows/publish-images.yml — also set those packages public. Bumping one CLI pin does not re-download the others. Node 22 and Python 3.11 are baked (not Features). Workspace npm ci / Playwright stay in post-create.
  2. updateContentCommand — post-create.sh --deps-only (npm, docs, Playwright)
  3. postCreateCommand — full post-create + doctor
    Full //:test is not a create gate (optional DEVCONTAINER_SMOKE=1).

Named volumes cache Bazel disk/repo, npm, pip, Playwright, and agent homes (~/.grok, ~/.hermes) across rebuilds.

Feature pins for Dev Container Features live in .devcontainer/devcontainer-lock.json (commit this file — same role as other lockfiles).

Troubleshooting

SymptomFix
Create failed / doctor redRebuild Container; check Docker is running; run bash .devcontainer/doctor.sh
docker missing in containerHost Docker must be running (docker-outside-of-docker uses the host socket)
Apple Silicon slow first buildExpected; caches make rebuilds much faster
Windows path issuesClone under WSL filesystem (\\wsl$\...), not a slow /mnt/c tree
Hermetic dashboard tests failNeed working docker build on the host engine
kcov / shell coverageLinux container only; macOS host skips coverage (validate still OK)
Stale Bazel cachedocker volume rm dgx-lab-bazel-disk dgx-lab-bazel-repo then rebuild
Node version mismatchContainer and CI use 22; set host Node 22 if not using the container
mkdir … ~/.grok/…: Permission deniedNamed volume dgx-lab-grok-home is root-owned. In-container: sudo chown -R "$(id -u):$(id -g)" ~/.grok ~/.hermes then bash .devcontainer/install-agent-clis.sh. Or on host: docker volume rm dgx-lab-grok-home dgx-lab-hermes-home and rebuild.
grok: command not foundImage pin missing — rebuild the container. Fallback: bash .devcontainer/install-agent-clis.sh then grok login --device-auth.
Host LiteLLM unreachableUse http://host.docker.internal:<port>/v1, not 127.0.0.1 (that is the container). Docker Engine needs Docker 20.10+ (host-gateway).
Grok cannot run dockerExpected under GROK_SANDBOX=lab. Run docker yourself, or GROK_SANDBOX=off for that session.
Feature lockfile driftCommit .devcontainer/devcontainer-lock.json; regenerate via Dev Containers rebuild / CLI when changing features.
Mypy / Pylance ENOENT on .venv-docs/bin/pythonHost macOS/Windows venv bind-mounted into Linux. Fix: rm -rf .venv-docs && bash docs/setup-docs.sh (post-create also recreates unusable venvs). IDE uses system Python 3.11 by default.
docs/manage-docs.sh status says venv unusableSame host venv issue; run docs/setup-docs.sh.
Hermes “tools disabled” / missing API keys at createExpected — create installs the CLI with --skip-setup --non-interactive. Run hermes setup only when you want Hermes.
Bazel extension “query failed” right after openFirst download of Bazel binary; post-create prewarms bazelisk version. Retry or wait for prewarm.
